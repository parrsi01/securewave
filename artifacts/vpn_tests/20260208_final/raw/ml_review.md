## 2. DATA LEAKAGE ASSESSMENT

**Rating: 6/10 -- MIXED**

### 2.1 Experiment Pipeline (`ml/experiment.py`) -- CLEAN

The experiment runner in `ml/experiment.py` uses `split_records()` from `ml/data.py` which performs a proper random shuffle and split (default 80/20, seeded). Training and test sets are constructed independently. The QoS and risk datasets are built from separate record lists (`train_records` vs `test_records`). XGBoost models are trained only on `X_*_train` / `y_*_train` and evaluated on `X_*_test` / `y_*_test`. Early stopping eval sets use test data, which is a minor concern (see below).

**Verdict:** No train/test contamination in the experiment pipeline.

### 2.2 Training Script (`scripts/train_models.py`) -- DATA LEAKAGE PRESENT

The production training script at `scripts/train_models.py` trains on ALL records without any hold-out split:

```python
records = load_data(data_path)       # ALL 10,000 rows
qos_stats = train_qos_model(records, qos_model_path)   # Trains on ALL
risk_stats = train_risk_model(records, risk_model_path) # Trains on ALL
```

The "test predictions" at lines 82-91 and 156-165 use hardcoded synthetic inputs, not held-out data. This means the shipped models (`data/models/qos_model.json` and `data/models/risk_model.json`) were trained on 100% of the available data with no validation split.

**Impact:** The models are overfit to the training distribution. Any accuracy numbers reported from running inference on the same dataset are artificially inflated. However, since the training data is entirely synthetic (generated by `generate_synthetic_data.py`), and the models will encounter real-world data in production that differs from the synthetic distribution anyway, the practical impact is moderate. The models will degrade to rule-based fallback if they perform poorly.

**Severity: MEDIUM** -- The shipped models have no honest generalization estimate. The experiment pipeline (`ml/experiment.py`) does proper splitting but is not used to produce the shipped model artifacts.

### 2.3 Risk Model Feature Engineering -- LABEL LEAKAGE

In both `scripts/train_models.py` (lines 114-133) and `ml/data.py` (lines 64-88), the risk model features are **derived directly from the target variable** (`risk_score`):

```python
login_failures = 0 if risk_score < 0.3 else int(risk_score * 5)
unusual_hours = 1.0 if risk_score > 0.4 else 0.0
ip_reputation = max(0.3, 1.0 - risk_score)
geo_anomaly = 1.0 if risk_score > 0.5 else 0.0
data_exfil = risk_score * 0.5 if risk_score > 0.3 else 0.0
session_anomaly = risk_score * 2 if risk_score > 0.2 else 0.0
```

Every feature except `reconnect_freq` (which comes from `disconnect_count`) is a deterministic function of `risk_score`. The model is learning to invert a known function, not detecting actual risk patterns. This is **textbook label leakage**.

**Impact:** The risk model will report near-perfect accuracy on synthetic data but has zero ability to generalize to real behavioral signals. In production, when real features (actual login failures, actual IP reputation lookups, actual geo data) are fed in, the model's predictions will be uncorrelated with true risk.

**Severity: HIGH** -- The risk model is methodologically invalid. It will only work correctly via its rule-based fallback.

### 2.4 QoS Labels -- Circular but Acceptable

The QoS labels in the synthetic data are generated by a rule-based function (`classify_qos()` in `generate_synthetic_data.py`, lines 46-62) that uses the same features the model trains on. The XGBoost model is essentially learning to replicate this rule-based function. This is circular, but since the rule-based fallback (`_rule_based_score()` in `xgb_qos.py`) uses nearly identical logic with similar weights, the practical impact is that the XGBoost model and the fallback produce similar results. The XGBoost model adds value only if it learns non-linear interactions the rule-based scorer misses.

**Severity: LOW** -- Circular but not harmful. The model at worst matches the fallback.

## 3. ANTI-POISONING ASSESSMENT

**Rating: 8/10 -- GOOD**

### 3.1 Server-Side Input Validation (`vpn_optimizer.py`)

The `_validate_metric()` static method (lines 180-188) provides solid input clamping:

```python
@staticmethod
def _validate_metric(value, min_val, max_val, default):
    v = float(value)
    if v != v:  # NaN check
        return default
    return max(min_val, min(max_val, v))
```

- **NaN detection:** Uses `v != v` idiom -- correct and efficient.
- **Range clamping:** All metrics are clamped to physical bounds (latency 0-10000ms, bandwidth 0-100000Mbps, CPU 0-1.0, etc.).
- **Type coercion:** `float(value)` handles string inputs; `TypeError`/`ValueError` caught with default fallback.
- **Coverage:** Applied to all 7 metric fields in `update_server_metrics()` (lines 200-214).
- **Feedback path:** `report_connection_quality()` (lines 436-437) also validates `actual_latency` and `actual_throughput` before they reach the Q-learning update.

**Gap:** No Infinity check. `float('inf')` passes the NaN check and the range clamp, but `max(0, min(10000, float('inf')))` returns 10000, which is the max bound -- so it degrades gracefully. Not a bug, but worth noting.

### 3.2 Client-Side Anti-Poisoning (`marlxgb.dart`)

The Dart predictor implements anomaly clamping in `predictBandwidth()` (lines 40-62):

```dart
final ratio = sample / previous;
if (ratio > anomalyThreshold) {
    safeSample = previous * anomalyThreshold;
} else if (ratio < 1 / anomalyThreshold && sample > 0) {
    safeSample = previous / anomalyThreshold;
}
```

- Threshold is 2.5x (configurable via constructor).
- Extreme spikes are clamped relative to the EMA, preventing single-sample poisoning.
- The `sample > 0` guard prevents division-by-zero on the low-ratio path.
- Final result is clamped to `[min, max]` (default 1-250 Mbps).

**Gap:** If `previous` is 0 and `sample` is negative, the early return at line 46-48 handles it via `sample.clamp(min, max)`. Negative bandwidth becomes 1 Mbps. Acceptable.

### 3.3 No Validation on QoS/Risk Model Inputs

The `QoSInput` and `RiskInput` dataclasses have no input validation. Callers could pass `latency_ms=-999` or `packet_loss=50.0` and the model would process it. The rule-based fallback clamps scores to [0, 1] via `max(0, min(1, ...))`, but the XGBoost model path does not validate inputs before inference.

**Severity: LOW** -- The models were trained on bounded data, so extreme inputs will produce extrapolated but bounded predictions. The final score is clamped in the risk scorer (`max(0.0, min(1.0, score))` at line 261 of `xgb_risk.py`). QoS uses `predict_proba` which returns probabilities summing to 1, so the output is inherently bounded.

## 4. FALLBACK SAFETY ASSESSMENT

**Rating: 9/10 -- EXCELLENT**

### 4.1 Three-Layer Fallback Chain

The system implements a clean three-layer degradation:

1. **Layer 1 -- Import guard:** ML dependencies (numpy, xgboost, sklearn) are lazy-imported with try/except. If unavailable, `ML_AVAILABLE = False` and all ML paths are skipped. The app starts and functions without any ML library installed.

2. **Layer 2 -- Training guard:** Even if ML libraries are available, models require explicit training or loading. `is_trained = False` by default. Untrained models fall back to rule-based scoring.

3. **Layer 3 -- Exception guard:** All ML inference paths are wrapped in try/except with fallback to rule-based scoring:
   - `xgb_qos.py` line 242: `except Exception: return self._rule_based_score(inp)`
   - `xgb_risk.py` line 279: `except Exception: return self._rule_based_score(inp)`
   - `vpn_optimizer.py` line 339: `except Exception: combined_value = q_value`

### 4.2 Optimizer Fallback

The server-side optimizer (`vpn_optimizer.py`) has its own fallback at line 343:

```python
else:
    # Fallback: Use reward function directly
    combined_value = q_value + 0.3 * self._calculate_reward(server, user_state)
```

When ML is disabled or has insufficient history (<100 samples), the optimizer uses direct reward calculation. This is a weighted heuristic combining latency, bandwidth, load, stability, and security -- reasonable defaults.

### 4.3 Client-Side Independence

The Dart predictor (`marlxgb.dart`) is completely independent of the server-side ML pipeline. It performs pure arithmetic (EMA, sigmoid scoring, linear weighting) with no network calls, no model loading, and no external dependencies. It cannot fail due to server-side ML issues.

### 4.4 Empty Server List

`select_optimal_server()` returns `{"error": "No servers available"}` when the server list is empty (line 388). Callers must handle this case.

**Only gap:** The `_select_server_marl()` method at line 349 does `list(self.servers.keys())[0]` as ultimate fallback, which would raise `IndexError` on an empty server list. However, this is guarded by the check at line 387-388 in the public method, so it is unreachable.

## 6. CLIENT-SIDE SAFETY

**Rating: 9/10 -- VERY GOOD**

### 6.1 Crash Safety of `marlxgb.dart`

The Dart predictor is a `const`-constructible class with no mutable state, no async operations, no file I/O, and no network calls. It cannot crash the app through:

- **Memory exhaustion:** No collections, no buffers, no allocations beyond stack frames.
- **Infinite loops:** No loops of any kind. All methods are O(1) per call.
- **Unhandled exceptions:** No exceptions are thrown. All arithmetic is on `double` and `int`.

### 6.2 NaN/Infinity Handling

- **`predictBandwidth()`:** If `previous <= 0`, returns `sample.clamp(min, max)`. If `sample` is `NaN`, `clamp` returns `NaN` in Dart -- this is a **gap**. `NaN.clamp(1, 250)` returns `NaN` in Dart (per IEEE 754). However, `NaN` would propagate as the EMA value, and subsequent calls with valid samples would blend it out (since `NaN * weight` remains `NaN`, the blend stays `NaN`). This is a sticky failure mode.

- **`scoreServer()`:** If `latencyMs` is `NaN`, `1 / (1 + NaN/60)` = `NaN`, and the total score becomes `NaN`. The `.clamp(0, 1)` at the end does not fix this (same IEEE 754 issue).

- **`scoreStability()`:** If both `successes` and `failures` are 0, returns 0.8 (safe default). Division by `effectiveTotal` is guarded.

- **Infinity:** `double.infinity` as input to `predictBandwidth()` would trigger the anomaly clamp (`ratio > 2.5`), capping `safeSample` at `previous * 2.5`. This is handled correctly.

**Severity: LOW-MEDIUM** -- NaN inputs can create sticky NaN state in the bandwidth predictor. In practice, telemetry values come from platform APIs that return valid doubles, but a defensive `isNaN` check would harden the predictor.

### 6.3 No Side Effects

The predictor has no side effects. It does not:
- Write to shared preferences or local storage
- Send network requests
- Call platform channels
- Modify global state
- Log user data

## 7. MODEL STALENESS

**Rating: 5/10 -- NEEDS WORK**

### 7.1 Current Update Mechanism

- **Shipped models:** `data/models/qos_model.json` (1.5 MB) and `data/models/risk_model.json` (286 KB) are static files bundled with the backend deployment.
- **Server-side incremental training:** The optimizer's `_train_xgboost_incremental()` (lines 458-495 of `vpn_optimizer.py`) retrains on the last 300 telemetry samples every 100 reports. This updates the in-memory model only; the model is not persisted to disk.
- **No model versioning:** There is no model version number, training timestamp, or integrity hash stored with the model files.
- **No auto-update:** There is no mechanism to push updated models to running instances or to the client.

### 7.2 Risks

1. **Server restart resets ML state:** If the server process restarts, the in-memory incremental training is lost. The system reloads from the static model files (or starts untrained if files are missing).
2. **No concept drift detection:** There is no monitoring for distribution shift between training data and live telemetry.
3. **Client predictor has no model:** The Dart predictor is pure arithmetic with hardcoded parameters. There is no model to update, which is actually a strength -- it cannot become stale in the traditional sense.

### 7.3 Mitigation

The rule-based fallbacks ensure the system continues to function even with stale or missing models. Model staleness affects optimization quality, not system availability.

## 9. ADDITIONAL FINDINGS

### 9.1 Exploration Rate Uses numpy RNG for Randomness

In `_select_server_marl()` (line 312), when ML is available, exploration randomness uses `np.random.random()` which is NOT cryptographically secure. This is acceptable for ML exploration (not a security function), but the non-ML path correctly uses `secrets.SystemRandom()`.

### 9.2 Q-Table State Space Reduction

The state hash at line 324-328 uses `user_id % 1000`, which means users with IDs that differ by multiples of 1000 share Q-values. This is an intentional memory optimization but could cause suboptimal recommendations for high-user-count deployments. With the LRU cache size of 10,000 entries, this is not a concern for the current scale.

### 9.3 Health Monitor DB Session Management

`vpn_health_monitor.py` creates a new `SessionLocal()` on every 30-second cycle (line 51) and closes it in a finally-style block (line 81). However, if `check_all_servers()` raises before `self.db` is assigned, the `if self.db:` check at line 85 references the previously-set `None` value -- safe, but the pattern is fragile. A context manager would be more robust.

### 9.4 Demo Metrics Are Non-Deterministic

The health monitor's `_generate_demo_metrics()` uses `secrets.SystemRandom()` for demo server jitter, which means demo metrics vary between runs. This is fine for demo purposes but makes testing non-reproducible.

### 9.5 Incremental Training Trigger Condition

The incremental training in `vpn_optimizer.py` line 455 triggers when `len(self.metrics_history) % 100 == 0`. Since the deque has `maxlen=5000`, once full, every `update_server_metrics` call keeps the length at 5000, and the modulo check will only trigger when the length happens to be exactly divisible by 100. After the deque is full, the length stays at 5000 (which IS divisible by 100), so every single update triggers retraining. This is a bug -- the deque length stops growing at maxlen, so the modulo condition becomes permanently true.

**Severity: MEDIUM** -- After 5000 samples, every quality report triggers a full XGBoost retrain on 300 samples. This wastes CPU but does not cause incorrect behavior.

## 12. RECOMMENDATIONS

### Must-Fix Before Launch

1. **ML-3: Fix incremental training trigger.** Replace `len(self.metrics_history) % 100 == 0` with a counter-based approach:
   ```python
   self._report_count = 0
   # In report_connection_quality():
   self._report_count += 1
   if self.use_ml and self._report_count >= 100:
       self._train_xgboost_incremental()
       self._report_count = 0
   ```

### Should-Fix Before Launch

2. **ML-4: Add NaN guard to Dart predictor.** Add `if (sample.isNaN || sample.isInfinite) return previous.clamp(min, max);` at the top of `predictBandwidth()`. Similarly guard `scoreServer()`.

### Post-Launch

3. **ML-1: Rebuild risk model training pipeline.** Generate synthetic risk features independently of the target variable. Use behavioral simulation (random login failure counts, random geo-anomaly flags) with a separate labeling function that combines them into risk scores.

4. **ML-2: Use experiment pipeline for production models.** Run `ml/experiment.py` with a proper train/test split and persist the trained model from the experiment run, not from `train_models.py`.

5. **ML-5: Add model versioning.** Store training timestamp, data hash, and model version alongside model files. Log model version at startup.

## 13. LAUNCH READINESS VERDICT

**CONDITIONAL PASS -- Safe for launch with caveats.**

The ML pipeline is safe for production deployment. The advisory-only guarantee is rock-solid -- the optimizer cannot modify kill switch, DNS, or protocol settings under any circumstances. Fallback behavior is robust across all three layers (import guard, training guard, exception guard). Anti-poisoning guards are comprehensive on the server side.

The risk model is methodologically invalid (ML-1) but this is mitigated by the rule-based fallback, which will be the de facto risk scorer until the training pipeline is fixed. The QoS model provides marginal value over its rule-based equivalent, which is acceptable.

The incremental training bug (ML-3) should be fixed before launch to prevent unnecessary CPU waste. The Dart NaN gap (ML-4) is low-probability but easy to fix.

**Adjusted Final Score: 76/100** (down from 85 due to risk model leakage and training trigger bug)
