# SecureWave 4.0.0+12 usage recording candidate

This release adds account-owned, persistent WireGuard usage history.

The contract-15 Linux helper samples real peer transfer counters every two
seconds and saves cumulative checkpoints in root-owned, mode-0600 journals
under `/var/lib/securewave/usage`. The separate `securewave-meter` system
service reports every ten seconds and immediately reports completed sessions.
It has no Linux networking privileges, private keys, or account access tokens.
Its session-scoped capability permits reporting only one connection.

The helper tracks the connecting process using a pidfd. Window close, process
death, logout, disconnect, and orderly system shutdown capture a final
measurement and remove the tunnel. Reporting failures retain checkpoints for
replay. Unexpected counter resets, helper recovery, and abrupt interruption
produce an explicit measurement-gap flag rather than estimated bytes.

The backend stores cumulative v2 events, applies only new deltas under a
PostgreSQL row lock, and atomically records final totals. Server-side peer
snapshots have separate fields and cannot overwrite the ledger. History is
owner-scoped at `GET /api/vpn/usage/sessions`. Existing v1 endpoints and records
remain supported. Unrecorded historical traffic is not reconstructed.

Deployment uses the additive migration in `scripts/migrate_usage_recording.py`.
Legacy production protocol support is retained when preparing the backend
overlay. Account authentication, client-owned WireGuard keys, production
secrets, and unrelated workspace artifacts remain outside the changes.

## Verification status before publication

- Backend suite: 52 tests passed, including real PostgreSQL concurrent retry
  and additive migration checks against a disposable database.
- Flutter: analysis passed; 18 tests passed.
- Native helper: fixed-operation checks, durable replay, large counters,
  reset-gap handling, scoped acknowledgements, and pidfd process-death tests.
- Release binary compiled on ARM64.
- Installed GUI traffic, production persistence, close/crash/reconnect,
  reboot, package installation, and public delivery are separate acceptance
  gates. They must be recorded before treating this candidate as published.

The GUI retains its existing layout and adds a usage-recording status message.
There is no new history screen and no automatic application updater.
