# SecureWave 4.0.0+11 — Linux ARM64

This release saves the working Ubuntu 24.04 ARM64 application baseline.
The user confirmed the installed application is fully functional on 2026-10-04.

## Changes

- Registration explicitly sends an unauthenticated request, even if the API
  service previously held an expired token.
- HTTP 401 handling distinguishes rejected login credentials, unexpected
  registration authorization failures, and expired protected sessions.
- Expired sessions clear the stored token and open Sign in with an explanatory
  notice instead of opening Create account.
- Production's HTTP 400 duplicate-account envelope displays "An account with
  this email already exists" rather than asking users to change their fields.
- App, repository, and source-controlled release metadata use 4.0.0+11.
- Documentation records the current stack and freezes working behavior for
  the next UI-only changes.

Authentication continues to reject incorrect passwords. No authorization
checks were bypassed and no production authentication or VPN code was changed
by these client fixes.

## Install

Download `securewave-vpn_4.0.0+11_arm64.deb` from this GitHub release or
https://www.securewaveapp.com/download.html. From its directory:

```sh
sudo apt install ./securewave-vpn_4.0.0+11_arm64.deb
```

Open SecureWave VPN from Applications. This is an ARM64 Debian package, not
an x86-64 or cross-platform build. The release assets include package integrity
and source-provenance records; the old core verification tag remains intact.

## Installation-output explanation

The supplied APT output shows a successful upgrade from 4.0.0+10 to 4.0.0+11
using the local 15.1 MB package. The helper service was removed from the enabled
service links during upgrade and then re-enabled by the new package. Desktop
and icon indexes were refreshed. APT removed no unrelated packages; the long
autoremove list is an informational suggestion, and 62 unrelated updates were
left pending.

The `_apt` permission notice means that the restricted APT download user could
not read the package under the user's home directory, so APT read this local
file as root. It did not prevent installation. No services, sessions, containers,
or VM guests required an additional restart according to the displayed scan.

Mesa/EGL/Zink graphics warnings and the GDK cursor-theme warning occurred during
launch after installation. Given the user's confirmed functional window, they
were nonfatal graphics/theme warnings in this VM, not evidence of an auth or
package-install failure. They should be revisited only if rendering actually
breaks.
